## 一、项目定位与核心判断

### 1.1 一句话定义

一个以高品质内容策展 + 结构化项目数据库为核心的产品发现平台，面向所有"自己动手把想法变成产品"的人——在注意力稀缺的时代，做一个值得信任的过滤器。

### 1.2 市场判断依据

Vibe Coding 浪潮正在创造一个全新的用户群体——他们不是传统程序员，而是产品经理、设计师、运营、甚至完全没有技术背景的人，第一次能用 AI 把想法变成产品。这个群体正在爆发式增长，但目前在中文互联网没有归属地。即刻太杂、V2EX 太技术、CSDN 太丑、w2solo/独立开发很酷 质量太低、微信群太封闭。

同时，信息过载使得"被发现"成为所有 maker 的核心痛点。他们需要一个有品味的平台来展示自己的作品，也需要一个高效的渠道来发现值得参考的同行案例。

### 1.3 核心价值主张

对浏览者：在海量噪音中找到真正值得花时间了解的项目和洞察——每个推荐都让你有收获。

对创始人：一个有品质感的展示平台，比即刻帖子更持久，比自建官网更省事。被收录本身就是一种认可。

### 1.4 项目来源范围

不限于国内。标准是"对中文世界的 maker 有参考价值"——全球有意思的个人产品都在收录范围内。一个印度人用 Cursor 做了月入 $5000 的工具，如果路径对中文用户有启发，就收录。海外项目由 AI 辅助翻译和本地化语境解读。

### 1.5 定位边界

本平台不是：
- 不是 Product Hunt（不是发布/投票平台，是发现/策展平台）
- 不是技术论坛（不讨论代码和框架，讨论产品和商业）
- 不是自由发帖社区（不做 UGC 信息流，做编辑策展+结构化数据）
- 不是 AI 导航站（不做工具收集，做产品案例策展）

### 1.6 你的角色定位

产品 CEO + 主编。定品牌调性、做选品决策、设计产品体验、把控内容质量。日常执行层面可交给弟弟、招人、或 AI。但选品品味和产品审美是你亲自把关的核心，不外包。

## 二、目标用户

### 2.1 用户画像

**画像 A：想做副业的程序员**
- 有技术能力但不知道做什么
- 需要灵感、赛道判断、可参考的成功路径
- 高频搜索："什么产品能做""独立开发赚钱""micro SaaS idea"
- 在平台上的行为：按赛道浏览、对比同类项目、看增长方式

**画像 B：非技术背景的 Vibe Coder**
- 想用 AI 做产品但不确定怎么开始
- 需要"跟我背景相似的人做了什么"的案例鼓励
- 高频搜索："不会代码怎么做产品""AI 做 app""零基础创业"
- 在平台上的行为：按创始人画像浏览、看构建门槛、学习 Build Story

**画像 C：已有产品的创始人**
- 卡在获客阶段，技术没问题但不知道怎么推广
- 需要实战获客经验和同行交流
- 高频搜索："独立开发推广""冷启动方法""SEO 获客"
- 在平台上的行为：按增长方式浏览、看同赛道竞品、提交自己的项目获得曝光

### 2.2 画像在产品决策中的应用

每个候选项目至少命中一个画像才值得收录。AI 筛选阶段从三个画像视角分别打分。

## 三、竞品深度分析

### 3.1 Indie Hackers（核心参考对象）

**产品结构五层：**
1. 社区信息流（用户自由发帖，upvote 排序）——首页主体，流量大头，但噪音多
2. Case Studies / Stories（编辑"IndieJames"一人撰写的深度创始人访谈）——核心付费内容
3. Ideas DB（手工撰写的 80+ 公司深度报告）——付费内容
4. Products DB / Build Board（用户自主提交，每日投票排行）——参与度不高
5. 社区服务（Jobs、Partner Up、Meetups）——辅助功能

**关键洞察：**
- 真正让人付费的是编辑写的深度 Case Study，不是数据库
- 所有深度内容由一个人（IndieJames）撰写，证明"一人策展"模式可行
- Build Board 参与度低（排名第一帖子仅 33 upvote），说明"日更投票排行"机制对此用户群吸引力有限
- Products DB 的筛选维度值得学习（Stripe 验证收入、承诺度、融资状态）
- 最近新增"Vibe Coding Tools"导航 tab，说明在追热点但还没深做

**我们的差异化机会：**
- 中文原生，用中文用户视角策展全球内容
- 不做自由发帖社区（避免噪音），只做结构化策展
- 设计品质远超 Indie Hackers（这是我们的核心长板）
- 分类体系更贴合用户决策维度（不只是按行业分）

### 3.2 国内现有平台

| 平台 | 现状 | 为什么没做起来 |
|------|------|---------------|
| w2solo | 传统论坛形态，活跃度极低 | 设计粗糙、无品质感、无差异化内容 |
| 独立开发很酷 (solodev.cool) | 被各云厂商 SEO 软文推广 | 网站不稳定、内容靠搬运、品牌没有辨识度 |
| solo.xin | 小社区 | 规模太小、无品牌影响力 |
| GitHub chinese-independent-developer | 静态列表 | 不是产品，是资源汇总，无结构化无交互 |
| 即刻"独立开发"话题 | 最活跃的非正式聚集地 | 社交信息流形态，内容转瞬即逝，无结构化沉淀 |

**核心结论：** 国内没有一个高品质的、结构化的、有品牌调性的独立产品发现平台。现有玩家全部质量低、设计糙、没有形成真正的品牌认知。市场空白是真实的。

## 四、产品架构

### 4.1 核心双引擎

**引擎一：内容策展（流量引擎 + 品牌基础）**

精选优质个人/小团队产品，写成有洞察的推荐和深度拆解。每条推荐的核心不是介绍产品功能，而是提供一个让人有收获的洞察——"这个人做对了什么""这个赛道的机会在哪""从 0 到首笔收入他用了什么方法"。

内容形态分三档：
- 轻推荐（300-500 字，核心洞察+关键数据，适合社交平台传播）
- 深度拆解（1000-2000 字，完整故事弧+方法论提炼，平台独占内容）
- Featured Story（3000+ 字，对标 Indie Hackers Case Study，创始人深度访谈，后期付费候选）

**引擎二：结构化项目库（数据资产 + 用户留存）**

每个产品沉淀为标准化卡片。用户可按多维度浏览、筛选、对比、发现。创始人可提交和认领。数据越积越厚，越积越有价值。

两者关系：内容策展在前面拉流量和建品牌，项目库在后面做沉淀和留存。内容是鱼饵，项目库是鱼塘。用户可能因为一条小红书推荐进来，但因为项目库的浏览体验而反复回来。

### 4.2 页面结构概览

```
首页
├── 精选推荐区（编辑策展的精选项目，视觉重心）
├── 最新收录（近期新增的项目流）
├── 按维度快速入口（商业模式 / 构建门槛 / 增长方式 / 核心任务场景）
├── Radar 预览（数据洞察的精华摘要，MVP 用 demo 数据）
└── 提交入口 + 收录/认领说明

浏览/筛选页
├── 多维度筛选器（主分类维度 + 核心任务场景强标签 + tag 交叉筛选）
├── 排序选项（最新 / 最热 / 收入最高等）
├── 项目卡片列表（列表态）
└── 视图切换（卡片视图 / 紧凑列表视图）

项目详情页
├── 项目核心信息区（名称、描述、截图、分类标签、关键数据）
├── Build Story 区（创始人的构建故事，半结构化）
├── 智能关联导航区（同赛道项目 / 同增长方式 / 同创始人画像）
├── 赛道事实观察区（同类项目数量、商业模式分布、获客渠道分布等）
├── 衍生机会区（纯事实性观察，不做判断）
├── 互动区（结构化问答 / 收藏 / 分享）
└── 创始人信息卡

提交页
├── 自荐流程（URL → AI 预填 → 确认/修改 → 提交）
└── 他荐流程（URL + 一句推荐理由 → 提交）

Radar 页（MVP 为 demo）
├── 赛道趋势分析
├── 工具使用排行
├── 构建周期分析
└── 增长方式效果对比

反馈页
└── 结构化反馈入口（AI 友好）
```

### 4.3 首页设计逻辑

首页是品牌宣言——用户打开的前 3 秒必须感受到"这里不一样"。

**不做的事：** 不放自由发帖的信息流、不放投票排行榜、不放广告。

**做的事：** 
- 视觉焦点是编辑精选的项目（大卡片、高质量截图、一句话洞察）
- 快速维度入口让用户按自己的需求切入浏览（"我想看周末能做完的项目""我想看靠 SEO 起量的项目"）
- 核心任务场景入口直接回答用户当下的问题（"我在找副业方向""我想看非技术也能做出来的案例""我想看冷启动怎么做"）
- Radar 精华摘要让用户感知到"这个平台有数据深度"
- 整体感觉：像一本精心编排的杂志首页，不像一个论坛或信息流

### 4.4 项目详情页——智能关联系统

这是产品的核心差异化页面。当前设计不是一张静态卡片，而是一个探索起点。

**项目核心信息区：** 产品名、一句话描述、多张截图、赛道/阶段/商业模式等分类标签、关键数据点（收入区间、用户量、上线时间等，部分字段为创始人可选公开），并展示每个关键字段的数据来源、验证状态和更新时间。

**智能关联导航区（自动生成，无需编辑手动配置）：**

基于分类体系的结构化数据，自动展示：
- "同赛道的其他项目"——跟当前项目赛道相同的其他收录项目
- "相同增长方式的项目"——用了同样获客策略的项目
- "相似创始人画像的项目"——创始人背景相似的案例
- "相似构建门槛的项目"——开发周期/复杂度接近的项目

每个关联维度显示 3-5 个项目缩略卡片，可点击展开查看全部。这让用户从一个项目出发，顺着关联网络不断发现新内容，大幅提升在站时长。

**赛道事实观察区（自动生成，纯数据展示）：**

基于平台已收录的同赛道项目数据，展示：
- 同赛道已收录项目总数
- 商业模式分布（"8 个用订阅制，3 个一次性付费"）
- 获客渠道分布
- 平均构建周期
- 收入区间分布（如数据足够）

所有数据标注来源（"基于平台已收录的 XX 个同赛道项目"），不做价值判断，让用户自行解读。

**衍生机会区（谨慎处理 AI 幻觉风险）：**

只展示事实性观察，绝不做"这是一个好机会"类的判断。例如："当前收录的 12 个同赛道产品中，10 个面向英文市场，2 个面向中文市场"——这是事实。用户自己可以判断这意味着什么。

标注数据来源和时效性（"基于截至 2026-04-08 的平台数据"）。

### 4.5 北极星指标与核心漏斗

**北极星指标：每周深度发现会话数**

定义：一个会话中满足以下任一条件，即记为一次"深度发现会话"：
- 查看 3 个及以上项目详情页
- 或查看 1 个项目详情页后继续点击关联项目/筛选结果，并产生明显继续探索行为（如再次进入详情页或长停留）

这个指标衡量的不是空流量，而是用户是否真的在平台上"发现了值得继续看下去的东西"。它同时反映选品质量、详情页设计、关联导航和筛选体系是否成立。

**配套指标：**
- 首页/外部内容落地页 → 首个项目详情页点击率
- 详情页 → 关联项目二跳率
- 深度发现会话占总会话的比例
- 被收录创始人的回访/补充信息率
- 每周新增推荐/自荐数量

**浏览者漏斗：**
- 外部内容或搜索进入
- 打开首个项目详情页
- 通过关联项目或筛选继续探索
- 达成深度发现会话
- 后续产生推荐/收藏心智/再次回访

**创始人漏斗：**
- 被平台收录
- 收到人工触达或主动发现收录页
- 回站查看并补充/纠错
- 分享自己的收录页
- 后续继续更新信息或申请升级为精选

### 4.6 数据可信度机制

平台的所有"事实观察"都必须可追溯。原则上，AI 可以辅助提取和整理，但不能把猜测直接包装成事实。

**字段来源分层：**
- 公开页面抓取
- 第三方公开来源（采访、访谈、公开帖子等）
- 创始人补充/确认
- 编辑核验
- AI 推断（仅内部参考，不直接作为公开事实展示）

**对外展示规则：**
- 关键数据字段默认展示`来源`、`验证状态`、`最后更新时间`
- 没有可靠来源的精确数值不展示；宁可展示区间，也不展示伪精确数字
- 样本过小的统计不展示比例型结论，只展示事实描述或总量
- Radar 和详情页事实观察只使用可追溯字段，不使用纯推断数据
- 发现争议或来源冲突时，优先隐藏字段并开放纠错，而不是强行给结论

## 五、分类体系详细设计

### 5.1 设计原则

分类体系围绕用户决策维度构建，不围绕行业或技术。用户来这个平台问的不是"这属于什么行业"，而是"这个对我有什么参考价值"——我能做出来吗？能赚到钱吗？多快能做出来？怎么获客？

主分类维度要具备抗变性——不随 AI 工具迭代、技术栈更新、热点轮换而失效。

**信息缺失处理原则：** 早期项目的公开信息往往不完整——不知道增长方式、创始人背景不明确、商业模式还在探索中，这些都是正常状态。每个主维度都支持"待确认"状态，在 UI 上以自然的方式呈现（如淡色标签"待确认"或直接不展示该维度），避免为凑数据而硬猜。创始人认领后可自行补充，编辑策展时逐步完善。宁可留白，不可失真。

### 5.2 主分类维度

**维度一：商业模式**

| 分类 | 说明 | 用户决策价值 |
|------|------|-------------|
| 订阅制 (SaaS) | 按月/年收费 | 想做被动持续收入的人直接筛这个 |
| 一次性付费 | 买断制 | 想快速变现、不想做持续运营的人 |
| 免费增值 (Freemium) | 基础免费 + 高级付费 | 适合想快速积累用户再转化的策略 |
| 广告变现 | 靠流量和广告收入 | 适合内容型产品 |
| 交易抽佣 / 平台费 | 平台撮合交易抽成 | 适合做市场/平台型产品 |
| 开源 + 付费服务 | 开源核心 + 商业支持/托管 | 适合有技术背景想做开发者工具的人 |
| 内容/课程付费 | 卖知识、教程、数字产品 | 适合有领域专长的创作者 |

**维度二：构建门槛**

| 分类 | 说明 | 判定参考 |
|------|------|---------|
| 周末项目 | 几天内完成 MVP | 单一功能、简单交互、无复杂后端 |
| 月度项目 | 几周到一两个月 | 多功能、需要后端、有一定复杂度 |
| 持续工程 | 需要长期迭代维护 | 复杂系统、多端、需要持续运营 |

**维度三：增长方式**

| 分类 | 说明 | 适合什么人 |
|------|------|-----------|
| SEO 驱动 | 搜索引擎自然流量 | 有耐心做长期内容积累的人 |
| 社区 / 口碑驱动 | 社区传播和用户推荐 | 擅长社区运营和互动的人 |
| 内容营销驱动 | 通过博客/视频/社交媒体内容获客 | 有内容创作能力的人 |
| 付费投放驱动 | Google Ads / 社交媒体广告 | 有预算且懂投放优化的人 |
| 产品自传播 (Viral/PLG) | 用户使用过程中自然传播 | 产品本身有分享属性的项目 |
| 混合多渠道 | 上述多种方式组合 | 已经过了冷启动阶段的成熟项目 |

**维度四：创始人画像**

| 分类 | 说明 | 用户决策价值 |
|------|------|-------------|
| 技术背景转产品 | 程序员做自己的产品 | 技术人看"同类人怎么做的" |
| 设计师做产品 | 设计背景主导的产品 | 设计师看可参考路径 |
| 产品经理做产品 | PM 背景的创业者 | PM 看从需求到产品的实战 |
| 非技术用 AI 构建 | 完全非技术背景 | Vibe Coder 看"我也能做"的案例 |
| 小团队合作 | 2-5 人协作 | 想找合伙人的人看团队配合模式 |

**维度五：产品阶段**

| 分类 | 说明 |
|------|------|
| Idea | 纯想法阶段（仅 Idea 相关功能使用，不进入项目库主列表） |
| Building | 正在开发中 |
| Launched | 已上线可使用 |
| Revenue | 已有收入 |
| Scaling | 规模化增长中 |

### 5.3 核心任务场景（MVP 先做强标签）

这是比"项目属性"更贴近用户真实问题的一层。MVP 阶段先作为强标签出现在首页快捷入口、详情页关联区和浏览页筛选区；数据量足够后再考虑升级为一级筛选。

- 找副业方向：我想看值得抄作业的方向和切入角度
- 看周末可做项目：我想看低门槛、短周期、能快速上线的案例
- 看非技术 AI 构建案例：我想看不会写代码的人是怎么做出来的
- 看冷启动/获客打法：我想看别人怎么拿到第一批用户
- 看同赛道竞品：我想快速理解某个赛道现在都有哪些玩家
- 看中文市场/出海对比：我想判断市场选择和本地化机会

这些标签不直接从行业定义推导，而是基于项目结构化数据 + 编辑判断生成。目标是让用户一眼进入"我现在最关心的问题"。

### 5.4 辅助 Tag 体系

快速变化的维度全部做成可搜索可筛选的 tag，不做主导航：

- 赛道标签：效率工具、AI 应用、内容创作、电商/变现、教育学习、开发者工具、设计创意、生活服务、数据分析、社交通讯、金融理财、健康医疗、游戏娱乐……
- 工具标签：Cursor、Claude Code、v0、Bolt、Lovable、Windsurf……
- 技术栈标签：Next.js、React、Vue、Supabase、Firebase、Swift、Flutter……
- 市场标签：面向中文市场、面向英文市场、面向全球、出海产品……
- 平台标签：Web 应用、iOS App、Android App、Chrome 插件、微信小程序、API/SDK、CLI 工具……

### 5.5 分类体系的配置化

所有分类维度和选项从配置文件读取，不硬编码。后续调整分类、增加选项不需要改代码。Tag 体系支持动态增加。

## 六、投稿体系详细设计

### 6.1 设计原则

AI 时代的投稿不应该是填表，而是"用户给任何形式的输入，AI 负责结构化，人类只做确认和修正"。同时保持品质控制——不是所有提交都能获得同等展示。

### 6.2 自荐：创始人提交自己的产品

**提交流程（AI 原生交互）：**

最轻路径——用户只需做一件事：粘贴产品 URL。

然后平台自动完成：
1. 抓取页面截图
2. AI 分析页面内容，提取产品名、描述、功能要点
3. AI 建议赛道分类和标签
4. 生成一张预填好的卡片草稿

用户看到草稿后，确认或修改预填信息，补充 AI 无法获取的字段（当前阶段、构建门槛、收入区间等），提交。

备选路径——用户粘贴一段自由文本描述（比如他在即刻上发过的帖子内容），AI 从文本中提取结构化信息生成卡片草稿。

备选路径——用户上传截图，AI OCR + 理解后生成草稿。

核心：降低提交摩擦到最低，让 AI 做数据录入，人只做确认。

**三层展示分级：**

| 层级 | 门槛 | 展示位置 | 说明 |
|------|------|----------|------|
| 基础卡片 | 提交并通过最低验证 | 项目库可搜索，不在首页 | URL 必须可达，非 coming soon |
| 精选 | 通过编辑审核 | 首页展示，获得主要流量 | 项目质量、信息完整度、独特性达标 |
| Featured Story | 编辑深度采访/拆解 | 最高级别展示 | 未来付费内容候选 |

默认浏览只展示精选，基础卡片需切换"查看全部"。这样首页品质始终可控。

**最低门槛验证：**
- URL 自动可达性检测
- 非 coming soon / under construction 页面
- AI 能从页面中提取出有意义的产品信息（排除纯域名停放页）

### 6.3 他荐：用户推荐别人的产品

**提交流程：** 用户提交产品 URL + 一句推荐理由（为什么觉得这个产品值得关注）。

**发布机制（合规优化）：**

他荐项目经编辑审核后，发布前增加一步"尝试联系创始人"：
1. 查找创始人的公开联系方式（即刻/Twitter/邮箱/产品页面联系方式）
2. 如能找到，先发一条友好通知（"你的产品 XX 被推荐到我们平台，我们整理了一张介绍卡片，欢迎查看和认领"）
3. 不要求创始人回复同意才发布——通知是礼貌告知而非审批流程，3 天内无明确反对即可发布
4. 如找不到联系方式，直接发布

展示的是从公开信息中提取的内容（产品名、URL、功能描述、公开截图），这与科技媒体报道产品的逻辑相同，合法合规。发布后标注"此信息由平台整理，创始人尚未认领"。

这一步的核心价值不是合规审批，而是**建立创始人关系**——被主动告知的创始人更可能认领、补充信息、甚至主动传播。

**认领机制：**
- 给创始人保留"认领"入口——认领后可补充详细信息、修正不准确内容、获得"已认领"标识
- 保留"申请移除"入口——创始人不希望被收录可申请下架
- 认领通知：除上述发布前触达外，后续也可通过平台内入口发起认领

MVP 阶段先不做账号化认领。创始人通过表单/邮件/私信完成认领或修改申请，你人工处理；公开发布前的里程碑再补齐登录后认领能力。

**防刷：** 限每人每周推荐数量（如 3-5 个）。

### 6.4 里程碑更新（第二阶段功能）

定义关键里程碑节点：首次上线、首个用户、首笔收入、月入 ¥1000 / ¥5000 / ¥10000、用户数破百/千/万。

创始人到达里程碑时触发一次结构化更新，而非自由发帖。保证每条更新都有实质内容。

里程碑数据积累为 Radar/数据洞察提供核心数据源。

### 6.5 Build Story（创始人的构建故事）

半结构化模板引导，降低创作门槛，保证内容质量下限：

- 这个想法怎么来的？
- 用了什么工具和技术栈？
- 花了多长时间从 idea 到上线？
- 遇到的最大坑是什么？
- 怎么获取的前 100 个用户？
- 目前的数据和下一步计划？

创始人可以选填部分或全部。AI 可以基于创始人在其他平台的公开分享自动预填草稿。

### 6.6 创始人侧回流理由（MVP 先人工，后系统化）

创始人不是只来"领一次曝光"就结束。要让他愿意回来的理由足够具体：

- 收录页本身是长期可分享的外部页面，不是一条很快沉底的动态
- 创始人可以申请补充一句最新进展、修正错误信息、补截图或补 Build Story
- 优质项目可以从基础卡片升级到精选，形成明确的升级路径
- 被精选后平台提供现成的分享图和文案，降低他二次传播成本
- 创始人可以来增加 founder note

MVP 阶段这些动作以人工入口承接；公开发布前里程碑再做成登录后的标准化流程。

## 七、Idea 处理策略

### 7.1 Idea 来源

**第一层：项目采集的副产品。** AI 扫描时发现的"有人提了想法但没做出来"的内容——即刻帖子、Product Hunt 评论、Reddit 痛点帖。

**第二层：已有项目的竞品空白。** 收录 10 个 AI 写作工具，发现都做英文没做中文小红书——这本身是一个 idea。

**第三层：用户/创始人互动中的需求信号。** 创始人更新里说"很多用户问我加 XX 功能但我没精力做"。

### 7.2 呈现方式

不单独设立 Idea 板块。Idea 作为项目卡片的衍生内容自然呈现在详情页的"衍生机会区"。

呈现原则：
- 只展示事实性观察，不做机会判断
- 标注数据来源和时效性
- 让用户自行得出结论
- 内部人机协作可用 AI 分析打分，但面向用户不做过强引导

### 7.3 远期演进

数据量 200+ 项目后，可加 Idea 聚合视图——把所有衍生机会汇总为可筛选列表，按赛道、按需求信号强度排序。这是 Idea 板块的自然诞生方式——从数据中长出来而非从零搭建。

## 八、账号、认领与订阅节奏

### 8.1 MVP 边界

- MVP 不做用户登录系统
- MVP 不做邮件订阅/微信订阅
- 收藏、关注赛道、订阅创始人更新暂不开放
- 提交项目、纠错、认领申请通过轻量表单 + 人工处理完成

冷启动阶段优先验证"内容是否值得看"和"收录是否有传播价值"，不在最早阶段引入账号和订阅系统的复杂度。

### 8.2 公开发布前里程碑

在真正对外宣传发布前，单独补一个"触达与回流基础设施"里程碑，至少完成：

- 登录/身份确认（优先服务认领和补充资料）
- 认领后的基础编辑能力
- 至少一种订阅通道（优先邮件摘要；微信视主体条件接入）
- 收录/精选通知模板

### 8.3 上线前要验证的价值钩子

等账号体系启动时，注册的价值感必须真实可感，不能只是"收藏"（大多数人用浏览器书签替代）。

核心钩子：
- 关注某个赛道 → 有新精选项目时收到通知
- 订阅某个创始人 → 他的里程碑更新推送给你
- 认领自己的产品并持续补充信息

### 8.4 反馈系统

MVP 必须有结构化反馈入口——不是自由文本框，而是：

- 预设反馈类型选择（"信息有误""建议增加某个项目""功能建议""其他"）
- 类型选定后展示对应的结构化字段
- 收集的反馈数据结构化存储
- AI 可直接读取和分析反馈数据（AI 友好的数据格式）
- 定期 AI 汇总反馈趋势，辅助产品决策

## 九、Radar 数据洞察（MVP 为 Demo）

### 9.1 MVP 阶段

一个精心设计的 demo 页面，用模拟数据展示未来能力。设计品质要高——它是产品远景的视觉承诺。

Demo 展示内容：
- 赛道热度趋势图（"过去 3 个月哪些赛道的新项目最多"）
- 工具使用排行（"最多项目使用的 AI 工具 Top 10"）
- 构建周期分析（"平均从 idea 到上线需要多长时间"）
- 增长方式效果对比（"不同获客渠道的项目到达首笔收入的平均时间"）

标注"基于 XX 个项目的模拟数据，真实数据即将上线"。

### 9.2 真实数据版（100+ 项目后）

切换为真实数据驱动。AI 自动生成洞察摘要。编辑审核后发布。只有在字段来源、验证状态和样本量达到最低要求时，才展示比例型统计和趋势结论。

## 十、人机协作工作流详细设计

### 10.1 战略定位

这是整个项目最核心的基建。它决定了你能以多高的效率产出多高质量的内容和数据。需要做成一个完整的系统而非松散的脚本集合。

### 10.2 信息源配置

#### 第一梯队（MVP 先接入，数据获取难度低）

**即刻：**
- 获取方式：RSSHub 支持即刻话题的 RSS 输出
- 目标话题：独立开发、产品经理创业、AI 工具、Vibe Coding 等
- 数据质量：中高——创始人自己发的帖子信息密度较高
- 更新频率：每日

**Product Hunt：**
- 获取方式：官方 GraphQL API（合规，有 rate limit）
- 目标范围：每日新品，重点关注 solo/small team 的项目
- 数据质量：高——结构化信息完整（产品名、描述、截图、投票数、评论）
- 更新频率：每日

#### 第二梯队（工作流跑通后扩展）

**V2EX：**
- 获取方式：V2EX 有公开 API
- 目标版块：分享创造、推广
- 数据质量：中——技术讨论多，产品信息需要提取

**GitHub：**
- 获取方式：GitHub API 监控特定 repo（chinese-independent-developer 等）
- 数据质量：中——列表形式，需要进一步调研每个项目

**Indie Hackers：**
- 获取方式：尝试 RSS，或定期人工浏览 + AI 处理
- 数据质量：高——有收入数据、创始人故事
- 特殊价值：海外案例的核心来源

#### 第三梯队（反爬壁垒高，以人工+AI 处理为主）

**小红书：** 反爬强，前期人工浏览时遇到好项目手动录入或截图让 AI 提取。

**Twitter/X：** API 受限且价格高，前期人工浏览 #buildinpublic 标签 + AI 辅助。

### 10.4 AI 评分标准的建立与迭代

**冷启动期（第一周）：**
完全手动选品，不用 AI 筛选。自己从原始信息里挑。记录每个选择/拒绝的决策和理由。

**标准建立期（第二周）：**
用第一周的 10-20 个案例（含选择和拒绝的）作为 few-shot 示例写进 AI prompt。开始让 AI 辅助筛选，但你对比 AI 筛选结果和自己的判断，校准偏差。

**持续迭代期（第三周起）：**
持续用你的新决策更新 prompt 中的示例。当你发现 AI 漏选了好项目或错选了低质量项目，分析原因，调整评分维度和权重。每两周做一次 prompt review。

### 10.5 工作流的质量控制

- 每条发布的内容，你都要亲自看一遍最终版（不能完全依赖 AI 草稿）
- 每周回顾本周推荐的内容，评估哪些反响好哪些不好，优化选品方向
- 每月回顾分类标签的准确性，修正系统性偏差
- 反馈系统收集的用户意见纳入迭代

## 十一、营销策略详细设计

### 11.1 整体营销框架

```
内容营销（核心引擎）
├── 小红书（主要曝光，高流量）
├── 即刻（主要转化，可放外链）
└── 平台自身内容（SEO + AI 搜索收录）

主动触达增长
├── 被收录创始人的人工触达
├── 认领/补充资料邀请
└── 分享图和文案降低传播成本

产品驱动增长
├── 分享卡片自动生成（社交裂变）
├── 创始人认领后自发传播
└── "被收录"作为社交货币

长期渠道
├── SEO（项目库页面长尾排名）
├── AI 搜索优化 (GEO)
└── 口碑传播
```

### 11.2 小红书内容策略

**内容形态：** 精美卡片图（1-3 张）+ 精华文案（200-500 字）

**卡片图模板设计：**
- 提前设计 2-3 套高品质模板，每次只换内容
- 模板要素：产品名、一句话洞察、关键数据、产品截图、平台 logo 水印
- 配色/字体/排版要形成品牌一致性——看到卡片图就知道是你的平台
- 尺寸适配小红书推荐（3:4 或 1:1）

**标题公式（爆款思维）：**
- 数字 + 痛点/共鸣："这个人 3 天做了个月入 ¥8000 的产品，只因为做对了一件事"
- 反常识："不会写代码的设计师做了个 App，第一个月就赚了钱"
- 好奇心缺口："为什么这个看起来很简单的工具能月入 $5000？"
- 身份共鸣："上班族的第一个副业产品，上线当天就有了付费用户"

**话题标签策略：**
- 核心标签：#独立开发 #一个人做产品 #副业 #AI创业
- 趋势标签：#vibecodeing #AI工具 #产品推荐
- 人群标签：#程序员副业 #设计师创业 #产品经理
- 每篇根据内容选 5-10 个标签

**发布时间：** 工作日晚 7-9 点，周末下午 2-5 点（小红书用户活跃高峰）

**互动策略：**
- 每条推荐里留一个互动钩子（"你觉得这个赛道还有机会吗？""你会用什么方式做类似的产品？"）
- 及时回复评论，建立互动关系
- 评论区 pin 有价值的补充信息

**频率：** 每周 3 条推荐。可做成周更合集（"本周最值得关注的 3 个独立产品"），也可以单条发布。测试两种形式的数据后决定。

### 11.3 即刻内容策略

**内容形态：** 深度推荐文（500-1000 字）+ 产品链接 + 平台链接

**发布话题圈：** 独立开发、产品经理的日常、AI 探索、创业日记

**内容角度侧重：** 比小红书更深入——不只是"介绍一个产品"，而是拆解产品决策、获客策略、商业模式选择的逻辑。即刻用户偏好有思考深度的内容。

**互动策略：**
- @被推荐的创始人（如果他们在即刻上）
- 参与相关帖子的讨论，自然引流
- 分享做这个平台本身的过程（适度，不是 build in public 主线但偶尔穿插）

### 11.4 SEO 策略

**URL 结构：**
- 项目详情页：`/project/[slug]`（slug 用产品名的英文/拼音）
- 分类浏览页：`/browse/[dimension]/[value]`
- 赛道页：`/tag/[tag-name]`

**每个页面的 SEO 要素：**
- title：`产品名 - 一句话描述 | 平台名`
- description：项目简介 + 关键数据
- 结构化数据标记（Schema.org Product / SoftwareApplication）
- OG 图（自动生成的分享卡片图）

**长尾关键词策略：**
- 每个项目卡片页天然命中长尾搜索（"XX 产品怎么样""XX 替代品"）
- 分类浏览页命中中等竞争度关键词（"SEO 驱动的独立产品""周末能做完的副业项目"）
- 深度内容页命中高竞争度关键词（"独立开发赚钱""一个人做产品"）

### 11.5 AI 搜索优化 (GEO)

让平台内容对 AI 爬虫友好：
- 结构化数据标记（JSON-LD）
- 清晰的语义 HTML 结构
- FAQ 格式内容（适合 AI 引用）
- sitemap.xml 维护
- robots.txt 对主流 AI 爬虫开放

### 11.6 社交裂变机制

**分享卡片自动生成：**
- 每个项目详情页有"分享"按钮
- 点击生成一张设计精美的分享图（含产品名、一句话描述、关键数据、二维码/短链）
- 创始人分享"我的产品被 XX 平台收录了"→ 他的粉丝看到 → 访问平台
- 分享图的设计品质要高到"创始人愿意发朋友圈"的程度

**"被收录"的社交货币效应：**
- 收录通知的措辞要让创始人觉得被认可（"你的产品 XX 已被平台精选收录"）
- 提供现成的分享文案和图片，降低创始人分享成本
- 可考虑做一个"收录徽章"图片，创始人可以放在自己的产品页面上

### 11.7 冷启动增长链路（首个可执行闭环）

MVP 阶段的增长不要只依赖平台算法或自然 SEO，要有一条你今天就能执行的闭环：

1. 你每周发布 2-3 个精选项目和对应外部内容
2. 每个项目发布后，主动联系被收录创始人，给到收录页和分享卡片
3. 创始人回站查看、补充信息、转发给自己的受众
4. 新用户从单个项目进入后，通过关联项目、筛选和任务场景继续探索
5. 其中一部分用户再提交新项目或推荐别人产品，进入下一轮策展

这条链路在 MVP 阶段以人工触达为主，不依赖订阅系统先跑通。

## 十二、开发策略与里程碑

### 12.1 核心原则

**视觉/交互先行：** 在写任何业务逻辑代码之前，先做一版纯视觉和交互的最小确认集。用高保真 HTML/CSS（或 Figma）确认设计语言、核心页面布局、关键交互流程。确认满意后再进入业务开发。

**解耦架构：** 所有跟外部服务对接的地方都通过中间层封装。数据访问层、文件存储层、通知层、AI 调用层——每个都是可替换的插件。MVP 用最简实现，后期可无痛迁移。

**配置化：** 分类体系、标签体系、筛选选项全部配置文件驱动。

**迁移友好：** 前期部署海外（Vercel），后期需切回国内。代码不绑定 Vercel 独有特性，数据访问层支持从本地 JSON 到 Supabase 到国内 RDS 的渐进迁移。存储层用 S3 兼容 API，可从 Cloudflare R2 切换到阿里云 OSS。

### 12.2 MVP 里程碑规划（4-5 天）

**Day 0-1：视觉确认**

在写业务代码之前：
- [ ] 确定 Design Token（色彩体系、字体、间距、圆角、阴影等）
- [ ] 确定品牌名和 Logo 方向
- [ ] 做首页静态设计（可直接写 HTML/CSS）
- [ ] 做项目卡片的列表态和详情态设计
- [ ] 做提交流程的交互原型
- [ ] 确认移动端响应式的关键断点和布局

视觉确认的标准：截图发给 2-3 个朋友看，第一反应是"这个做得挺好看的"。

**Day 1-3：核心功能开发**

- [ ] 项目首页（精选展示 + 维度入口）
- [ ] 浏览/筛选页（多维度筛选 + 卡片列表）
- [ ] 项目详情页（核心信息 + 智能关联导航 + 赛道事实观察）
- [ ] 自荐提交流程（URL → AI 预填 → 确认）
- [ ] 他荐推荐表单
- [ ] 反馈入口
- [ ] 数据访问层（本地 JSON，接口预留迁移能力）
- [ ] 基础 SEO（meta、OG 图、结构化数据）
- [ ] 深色模式适配（Design Token 暗色变量 + 主题切换 + 全页面验证）

**Day 3-4：内容与工作流**

- [ ] 小红书卡片模板设计完成（2-3 套）
- [ ] 人机协作筛选工作流跑通一次完整流程
- [ ] 至少 10 个种子项目数据入库
- [ ] 至少 2-3 条推荐内容已发布到即刻/小红书
- [ ] 分享卡片自动生成功能

**Day 4-5：上线与基础设施**

- [ ] Vercel 部署，公网可访问
- [ ] 域名配置
- [ ] 备案申请提交（国内域名）
- [ ] Radar demo 页面
- [ ] 基础数据分析（访问量、页面浏览深度等）
- [ ] 分享给熟人体验，开始收集反馈
- 各项测试

**公开发布前里程碑（不属于 MVP）：**

- [ ] 登录/认领基础能力
- [ ] 至少一种订阅通道（优先邮件摘要）
- [ ] 收录/精选通知模板
- [ ] 创始人补充信息入口从人工处理升级为系统化流程

### 12.3 MVP 交付标准

- 公网可访问，主要页面加载 < 2 秒
- 移动端体验良好（小红书/即刻用户多在手机上）
- 至少 10 个种子项目，每个信息完整
- 提交流程可用，AI 预填功能正常
- 反馈入口可用，数据可被 AI 读取分析
- 至少 2 条推荐内容已在外部平台发布并有初步互动数据
- 明确不包含登录、邮件订阅、微信订阅等账号触达能力

### 12.4 12 周止损标准

8 周内 MVP 上线并开始公开推广。12 周时检查：
- 100+ 收录项目
- 1000+ 周活跃访客
- 有创始人主动提交项目（不全靠你手动录入）

未达标则停下来复盘——是产品不对、市场不对、还是执行不对。

## 十三、壁垒建设

**短期（0-3 个月）：品牌认知**
选品品味 + 设计品质 → "这个平台推荐的东西就是比别处好"。在注意力稀缺的时代，品牌信任是最有效的用户留存手段。

**中期（3-12 个月）：数据资产**
结构化项目数据持续积累。项目越多，筛选对比越有价值。同赛道的事实观察越准确。后来者从零积累需要大量时间。

**长期（12 个月+）：网络效应**
创始人在平台维护项目页面 → 形成迁移成本。用户依赖平台做产品发现 → 形成使用习惯。平台成为"个人产品"领域的权威参考源 → 品牌壁垒。

## 十四、变现路径（后期）

前期完全免费，专注流量和数据积累。变现不急，但要在产品设计时预留接口。

| 阶段 | 变现方式 | 条件 |
|------|----------|------|
| 中期 | 深度 Featured Story 付费（对标 IH+） | 有稳定的深度内容产出 |
| 中期 | 项目方付费推广位 / Featured 展示 | 有足够流量使推广位有价值 |
| 中期 | 面向创始人群体的品牌广告 | 有精准的用户画像数据 |
| 后期 | 高级数据筛选 / 趋势报告付费订阅 | 数据量 500+ 项目 |
| 后期 | 付费咨询匹配 / 经验交换 | 有活跃的创始人社区 |

## 十六、关键风险与应对

| 风险 | 严重性 | 应对策略 |
|------|--------|----------|
| 冷启动无人来 | 高 | 先做内容建品牌，不做空平台等人。前 30 个项目自己填充。 |

| 内容质量不稳定 | 中 | 选品始终你亲自把关。AI 只做辅助不做决策。 |
| 被竞品复制 | 低 | 品味和品牌认知是真壁垒。速度和持续产出比保密更重要。 |
| 备案延迟 | 低 | 双域名策略——海外先上线，国内异步备案。 |
| AI 幻觉导致错误信息 | 中 | 面向用户只展示事实性观察，标注数据来源，不做强判断。 |
| 数据可信度被质疑 | 高 | 关键字段展示来源/验证状态/更新时间，小样本不展示比例型结论。 |
| 创始人不愿被收录 | 低 | 公开信息合法使用 + 保留申请移除入口。 |
| 功能贪多做不完 | 高 | 严格 MVP 定义，Day 1 先确认视觉再写代码。 |
| 坚持不下来 | 中 | 12 周止损线，8 周看结果。最大化自动化减少日常消耗。 |
| 海外→国内迁移困难 | 低 | 架构层面预留迁移口子，不绑定任何平台独有特性。 |

## 一、核心认知

### 1.1 我们在建什么

不是产品目录，不是信息聚合站。是**中文独立开发者生态的知识基础设施**。

高价值信息散落在各个平台——一条即刻帖子里藏着从 0 到 $5k MRR 的路径，一条评论里推荐了一个冷门但极好用的工具，一篇出海复盘沉在时间线底部再也没人看到。这些信息每天产生，每天消失。

Solobase 做的事：**系统性地收集、结构化、保存所有高信息密度的内容，然后用编辑品味筛选呈现。**

### 1.2 关键原则

1. **信息密度 > 产品链接** — 一条没有任何产品链接的经验帖，如果信息密度够高，同样值得收录。过滤标准是"值不值得一个 maker 花 2 分钟读"，不是"有没有可点击的链接"。

2. **源无关** — 数据系统不绑死任何特定渠道。即刻、PH、V2EX、小红书、Twitter、Newsletter、甚至微信截图——每个来源只是一个 adapter。处理管道完全源无关。今天有效的渠道明天可能失效，新的渠道随时可能出现。

3. **原始信息不可丢失** — 渠道标识、原始 ID、原始 URL、抓取时间、原始作者信息、互动数据、评论——所有元数据必须保留。加工是在原始数据之上叠加，不是替换。

4. **编辑层与数据层分离** — 原始数据层存的是事实（谁在什么时候发了什么内容）。编辑层存的是判断（通过/跳过/精选/加标签）。两层独立，编辑操作不修改原始数据。

5. **为合并而设计** — 同一个产品可能被即刻、PH、V2EX 同时提到。同一个 maker 可能在多个平台活跃。数据模型必须支持跨源实体合并。

## 二、数据模型

### 2.1 三核心实体

```
Product（产品）─────── Maker（创作者）
    │                      │
    │    多对多              │ 多对多
    │                      │
    └──── Content（内容）───┘
```

### 2.2 Product

一个可访问、可体验的具体产品。

| 字段 | 说明 |
|------|------|
| id | 内部唯一 ID |
| name | 产品名 |
| tagline | 一句话介绍 |
| description | 详细描述 |
| website | 产品主链接 |
| links | 其他链接（GitHub、App Store、Chrome Store、PH 页面等） |
| logo / screenshot | 产品视觉 |
| categories | 分类标签（AI工具/效率/开发者工具/Chrome扩展/移动App/...） |
| pricing | 定价模型（免费/Freemium/付费/开源） |
| status | 状态（active / dead / beta） |
| external_ids | 各平台上的 ID（PH ID、即刻帖子 ID 等） |
| created_at | 首次发现时间 |
| makers | → 关联 Maker |
| contents | → 关联 Content（所有提到这个产品的内容） |

### 2.3 Maker

独立开发者、设计师、vibe coder——产品背后的人。

| 字段 | 说明 |
|------|------|
| id | 内部唯一 ID |
| name | 名称 |
| avatar | 头像 |
| bio | 简介 |
| social_links | 各平台主页（即刻、Twitter/X、GitHub、个人网站等） |
| external_ids | 各平台上的 ID |
| is_claimed | 是否已认领（原生用户标记） |
| products | → 关联 Product |
| contents | → 关联 Content（这个人发布的所有内容） |

### 2.4 Content

所有高信息密度的内容单元。这是数据量最大的实体。

| 字段 | 说明 |
|------|------|
| id | 内部唯一 ID |
| source | 来源渠道标识（jike / producthunt / v2ex / native / ...） |
| source_id | 在来源平台的原始 ID |
| source_url | 原始链接 |
| type | 内容类型（见 2.5） |
| title | 标题（如有） |
| body | 正文全文 |
| media | 图片/视频 URL 列表 |
| external_links | 正文中提到的外部链接 |
| author_name | 原始作者名 |
| author_id | 原始作者在来源平台的 ID |
| engagement | 互动数据（likes, comments, shares） |
| top_comments | 高质量评论（带作者和点赞数） |
| published_at | 原始发布时间 |
| crawled_at | 抓取时间 |
| raw | 完整原始 JSON（兜底，防止任何信息丢失） |
| products | → 关联 Product |
| maker | → 关联 Maker |

### 2.5 Content 类型体系

| type 标识 | 说明 | 举例 |
|-----------|------|------|
| `product_launch` | 产品发布/上线 | "做了个 XX，今天上线了" |
| `revenue_report` | 收入/里程碑 | "MRR 到 $5k 了" |
| `build_log` | 开发过程/复盘 | "30天从想法到上线" |
| `tool_recommendation` | 工具/资源推荐 | "我用这套 stack 搞定了 XX" |
| `strategy_insight` | 策略/方法论 | "出海定价的 3 个坑" |
| `failure_postmortem` | 失败反思 | "为什么没做起来" |
| `market_observation` | 行业/趋势 | "AI 工具赛道的变化" |
| `user_feedback` | 使用体验/反馈 | "用了 XX 一个月的感受" |
| `tutorial` | 教程/指南 | "零基础 AI 编程教程" |
| `resource_collection` | 资源合集 | "整理的所有开源 skill" |
| `other` | 未分类但高密度 | 不确定分类但值得保留 |

## 三、信息密度评分

### 3.1 为什么不用"有没有链接"做过滤

实际审核数据证明：一些算法低分（10-11 分）的内容被编辑通过了（小而美的创意产品），而一些高分内容被跳过了（没有差异化的跟风产品）。编辑判断 ≠ 算法打分。

算法的作用是**把候选池从几千条缩小到几百条**，让编辑的时间花在刀刃上。不是替代编辑。

### 3.2 高信息密度信号（加分）

- 包含具体数字（收入、用户量、转化率、天数、成本）
- 包含具体步骤/流程（>100 字的结构化描述）
- 包含多个具名工具/产品/服务
- 包含外部链接（产品链接、代码仓库、教程地址）
- 包含图片/截图（产品截图、数据截图、流程图）
- 有高互动（点赞 > 20 或评论 > 10）
- 有高质量评论（评论中有补充信息、使用体验）
- 时间越近越好（近 1 月 >> 近 1 年 >> 1 年以上）
- 作者本身是有产品/有经验的 maker

### 3.3 低信息密度信号（减分/丢弃）

- 极短内容（<50 字 + 无链接 + 无图片）→ 直接丢弃
- 纯情绪表达（焦虑、感慨、吐槽）无具体信息 → 丢弃
- 招聘/求职/内推 → 丢弃
- 转发抽奖/营销水帖 → 丢弃
- 八卦/明星/企业内部事件 → 丢弃
- 内容太泛无法操作（"坚持就是胜利"类鸡汤）→ 丢弃

### 3.4 编辑品味补充维度（算法难以量化，人工判断）

- 产品有审美/创意（小而美，哪怕互动数据不高）
- 创始人故事有独特性（不是模板化的分享）
- 切入点冷门但有价值（"外卖比价工具"、"文学时钟"）
- 失败案例但有诚意的反思

## 四、数据采集架构

### 4.1 Adapter 模式

每个数据源是一个独立的 adapter，职责是：
1. 连接源平台（API / 爬虫 / RSS / 手动导入）
2. 拉取原始数据
3. 转换为统一的 RawItem 格式
4. 存储到 `data/raw/{source}/` 目录

```
data/raw/
  jike/              # 即刻原始数据
  producthunt/       # PH 原始数据
  {new_source}/      # 未来新渠道
```

### 4.2 已实现的 Adapter

| 渠道 | 脚本 | 模式 | 状态 |
|------|------|------|------|
| 即刻 | `scripts/crawl/jike.ts` | 圈子抓取 + 关键词搜索 | 已完成，2711 条 |
| Product Hunt | `scripts/crawl/producthunt.ts` | GraphQL API 按月拉取 | 运行中，3400+ 条 |

### 4.3 待探索的渠道（需用户验证方向）

- V2EX「分享创造」
- 小红书（反爬成本高，待评估 ROI）
- Twitter/X #buildinpublic
- GitHub Trending
- 竹白/Newsletter
- 微信公众号
- 其他用户在摸索过程中发现的渠道

### 4.4 处理管道

```
Raw Data → 信息密度过滤 → 实体提取 → 去重关联 → 跨源合并 → 人工审核 → 入库
```

每一步都是独立可替换的模块，不依赖特定渠道的逻辑。

## 五、编辑审核工作流

### 5.1 当前方案：飞书多维表格

- 飞书 Base: `KXYpb5pTUa5gnPsFe18cNaoVnzh`
- 按来源/批次建表，推送待审数据
- 审核状态：通过 / 跳过 / 待定
- 备注字段记录编辑判断（类型标签、关注点、疑虑）
- 两人协作：从两端向中间审核

### 5.2 审核判断标准（来自实际审核记录总结）

**通过倾向：**
- 有明确可用产品 + 创作者叙事
- 高信息密度的经验复盘（尤其万字长文型）
- 小而美 + 有创意/审美的产品
- 实用开源工具
- 出海实战经验
- MRR/收入里程碑分享

**待定倾向：**
- 需要下载体验才能判断的 App
- 有风险的灰色地带产品
- 已经很知名不确定收录价值的

**跳过倾向：**
- 无差异化的跟风产品
- 产品知名但不符合平台审美
- 信息密度太低的浅度推荐

## 六、冷启动 → 原生过渡

### 6.1 阶段定义

| 阶段 | 数据来源 | 重点 |
|------|----------|------|
| 冷启动（当前） | 爬取外部平台 | 积累高质量内容池，建立初始品牌感知 |
| 吸引期 | 爬取 + maker 发现自己被收录 | maker 来到平台，认领 profile |
| 过渡期 | 爬取 + 原生投稿 | maker 开始直接在平台发布内容 |
| 原生期 | 以原生为主，爬取为辅 | 社区自运转，爬取变为发现新 maker 的手段 |

### 6.2 Maker 认领机制

冷启动阶段自动创建的 Maker profile，当本人来到平台时：
- 认领已有 profile（"这是我"）
- 自动关联所有历史 Content 和 Product
- 补充/修正个人信息和产品信息
- 看到："你的产品 XX 已经被社区讨论了 15 次"

这让新用户的第一次体验不是面对空白页面，而是发现平台已经在关注他们。

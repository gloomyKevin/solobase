## 一、核心认知

### 1.1 我们在建什么

不是产品目录，不是信息聚合站。是**中文独立开发者生态的知识基础设施**。

高价值信息散落在各个平台——一条即刻帖子里藏着从 0 到 $5k MRR 的路径，一条评论里推荐了一个冷门但极好用的工具，一篇出海复盘沉在时间线底部再也没人看到。这些信息每天产生，每天消失。

Solobase 做的事：**系统性地收集、结构化、保存所有高信息密度的内容，然后用编辑品味筛选呈现。**

### 1.2 关键原则

1. **信息密度 > 热度** — 一条没有任何产品链接的经验帖，如果信息密度够高，同样值得收录。过滤标准是"值不值得一个 maker 花 2 分钟读"，不是"有没有可点击的链接"或"有没有足够多的点赞"。评分是排序工具，不是裁决工具——编辑判断永远高于算法分数。

2. **核心标准层 + 源特有扩展层** — 不绑死任何特定渠道。每个来源通过 adapter 转为统一的核心格式（公共字段：body、author、links、engagement），同时保留源特有字段（即刻的 topic、PH 的 makers/topics、V2EX 的 node）。核心处理逻辑源无关，但不抹杀源上下文。

3. **原始信息不可丢失** — 渠道标识、原始 ID、原始 URL、抓取时间、原始作者信息、互动数据、评论——所有元数据必须保留。加工是在原始数据之上叠加，不是替换。

4. **事实 / 推断 / 判断三层分离** — 原始数据层存事实（谁在什么时候发了什么）。推断层存算法产出（内容类型、提取的产品/maker 引用、密度评分）。编辑层存人工判断（通过/跳过/标签/备注）。三层独立，互不污染。

5. **为合并而设计，但允许回退** — 同一个产品/maker 可能在多个源出现。合并是链接关系而非覆盖——每个源记录保持独立，canonical 实体是聚合视图。合并错了可以拆开，不破坏原始数据。

6. **可以不用但不能没有** — 数据是平台壁垒的核心。每个字段、每条元数据、每个原始 JSON，哪怕当前前端不展示，也必须保留。原因：(1) 未来的产品形态可能需要今天想不到的字段；(2) 数据的时间深度是竞争对手无法追赶的护城河；(3) 重新抓取的成本远高于存储成本。具体而言：raw 字段永远保留、source_extra 不丢弃、推断层可重跑不污染事实层、编辑操作全部可追溯。

### 1.3 合规与信任底线

我们抓取的是公开社交媒体内容，但公开不等于无限制使用。基本规则：

| 场景 | 处理 |
|------|------|
| 内容前台展示 | 注明来源和原始作者，提供原帖链接 |
| 作者要求删除/不收录 | 立即从前台移除，原始数据标记为 `withdrawn` |
| Maker 认领 | 需要验证身份（比如在原平台发一条确认帖） |
| 头像/个人信息 | 仅展示公开可见的信息，不拼接推断隐私 |
| 内部字段 | engagement 原始数据、算法评分、编辑内部备注不公开 |

治理机制随平台发展逐步完善，但底线从第一天就不能模糊。

## 二、数据模型

### 2.1 三核心实体

```
Project（项目）─────── Maker（创作者）
    │                      │
    │    多对多              │ 多对多
    │                      │
    └────── Post（帖子）────┘

共享主题标签 → 按主题聚合呈现，用户按需求找，不按数据类型找
```

实体内部分三层：事实层（source，不可变）/ 推断层（inferred，算法产出）/ 编辑层（editorial，人工判断）。

**关键设计决策：** Project 和 Post 共享同一套主题标签体系（Topic），前端按 Topic 聚合查询，返回 Project + Post 的混合列表。用户看到的是"出海相关的一切"，不是"出海的产品"和"出海的帖子"分开两个地方。

### 2.2 共享主题标签（Topic）

Project 和 Post 都用这一套，是按主题聚合的基础：

```typescript
// 主题标签 — 随平台发展扩展
type Topic =
  | 'ai-tools'          // AI 工具
  | 'going-global'      // 出海
  | 'devtools'          // 开发者工具
  | 'productivity'      // 效率
  | 'design'            // 设计
  | 'side-project'      // 副业/Side Project
  | 'open-source'       // 开源
  | 'chrome-extension'  // 浏览器扩展
  | 'mobile-app'        // 移动应用
  | 'saas'              // SaaS
  | 'vibe-coding'       // Vibe Coding / AI 编程
  | 'monetization'      // 变现/商业化
  // ...
```

### 2.3 Project

maker 创造的可访问对象 — 产品、工具、开源仓库、模板、workflow 等。长期存在，不断更新。

**事实层：**

| 字段 | 说明 |
|------|------|
| id | 内部唯一 ID |
| slug | URL 标识 |
| name | 项目名 |
| tagline | 一句话介绍 |
| description | 详细描述 |
| website | 主链接 |
| links | 其他链接（GitHub、App Store、Chrome Store 等） |
| logo / screenshots | 产品视觉 |
| source_refs | 各平台记录引用（`[{source, source_id, url}]`） |

**分析维度（兼容现有前端模型）：**

| 字段 | 说明 |
|------|------|
| kind | 类型：app / tool / extension / template / resource / open_source / workflow |
| businessModel | 商业模式：subscription / freemium / one_time / open_source_plus / ... |
| buildEffort | 构建难度：weekend / monthly / ongoing |
| growthChannel | 增长渠道：seo / community / content_marketing / viral / ... |
| founderType | 创始人类型：tech_to_product / designer / non_tech_ai / small_team / ... |
| stage | 阶段：idea / building / launched / revenue / scaling |
| topics | **共享主题标签**（同 2.2） |
| tags | 其他标签维度：platform / market / techStack / tools（保留现有前端的 tag 结构） |
| metrics | 可验证指标：revenueRange / userCount / launchedDate（带来源+可信度标记） |
| buildStory | 构建故事：origin / toolsUsed / timeline / challenges / acquisition |

**编辑品味层：**

| 字段 | 说明 |
|------|------|
| editorial_status | 审核状态 |
| isEditorsPick | 编辑精选 |
| featuredInsight | 编辑提炼的一句话亮点 |
| vibes | 品味标签：`小而美` `设计感` `技术硬核` `创意切入` `出海标杆` `冷门有价值` `极简` ... |
| curatedCollections | 所属精选集 |
| editorNotes | 内部备注 |

**关联：**

| 字段 | 说明 |
|------|------|
| makers | → Maker[] |
| posts | → Post[]（所有关联帖子） |

### 2.4 Post

时间线上的内容单元。冷启动阶段 = 抓取的帖子；原生阶段 = maker 在平台上发布的内容。

**事实层（不可变）：**

| 字段 | 说明 |
|------|------|
| id | 内部唯一 ID |
| type | 帖子类型（见 2.6） |
| title | 标题（可选） |
| body | 正文全文（Markdown） |
| excerpt | 摘要（可自动截取） |
| media | 图片/视频 URL 列表 |
| externalLinks | 正文中的外部链接 |
| topics | **共享主题标签**（同 2.2） |
| source | 来源渠道：native / jike / v2ex / linuxdo / ... |
| sourceId | 在来源平台的原始 ID |
| sourceUrl | 原帖链接 |
| engagement | 互动数据 { likes, comments, shares, bookmarks } |
| topComments | 高质量评论 |
| publishedAt | 发布时间 |
| crawledAt | 抓取时间（冷启动数据有，原生数据无） |
| sourceExtra | 源特有字段（不可丢失） |

**推断层：**

| 字段 | 说明 |
|------|------|
| inferred_type | 算法推断的类型（编辑可覆盖） |
| inferred_projects | 从内容中识别的项目引用 |
| inferred_maker | 推断的 maker 关联 |
| density_score | 多维评分 { density, heat, timeliness, association } |
| density_signals | 评分依据明细 |
| crossRefs | 跨源匹配 |

**编辑层：**

| 字段 | 说明 |
|------|------|
| editorial_status | published / featured / archived / draft |
| editorial_type | 编辑确认的类型（覆盖推断） |
| editorial_tags | 编辑标签 |
| vibes | 品味标签（同 Project） |
| isFeatured | 精选 |
| editorNotes | 内部备注 |

**关联：**

| 字段 | 说明 |
|------|------|
| authorId | → Maker |
| projectIds | → Project[]（可选，0 到多个） |

### 2.5 Maker

独立开发者、设计师、vibe coder——Project 和 Post 背后的人。

| 字段 | 层 | 说明 |
|------|-----|------|
| id | - | 内部唯一 ID |
| name | source | 名称 |
| avatar | source | 头像 |
| bio | source | 简介 |
| backgroundType | source | 背景：tech_to_product / designer / non_tech_ai / small_team |
| socialLinks | source | 各平台主页 |
| sourceRefs | source | 各平台账号引用 |
| isClaimed | - | 是否已认领 |
| editorialNotes | editorial | 编辑备注 |
| projects | relation | → Project[] |
| posts | relation | → Post[] |

### 2.6 Post 类型体系

| type | 说明 | 举例 |
|------|------|------|
| `product_launch` | 项目发布/上线 | "做了个 XX，今天上线了" |
| `revenue_milestone` | 收入/里程碑 | "MRR 到 $5k 了" |
| `build_log` | 开发过程/复盘 | "30天从想法到上线" |
| `tool_recommendation` | 工具/资源推荐 | "我用这套 stack 搞定了 XX" |
| `strategy_insight` | 策略/方法论 | "出海定价的 3 个坑" |
| `experience_share` | 经验分享 | "独立开发两年总结" |
| `failure_postmortem` | 失败反思 | "为什么没做起来" |
| `market_observation` | 行业/趋势 | "AI 工具赛道的变化" |
| `tutorial` | 教程/指南 | "零基础 AI 编程教程" |
| `resource_collection` | 资源合集 | "整理的所有开源 skill" |
| `idea` | 想法/需求 | "帮设计师自动标注设计稿" |
| `user_feedback` | 使用体验/反馈 | "用了 XX 一个月的感受" |

### 2.7 按主题聚合的呈现策略

用户按需求发现内容，不按数据类型。前端按 Topic 查询，返回 Project + Post 混合列表：

```
用户点击「出海」→ 查询 topics 包含 'going-global' 的所有 Project 和 Post
  → Project 用产品卡片渲染
  → Post 根据 type 用不同卡片渲染（build_log 用文章卡片，revenue_milestone 用数字卡片...）
  → 按相关性/时间/编辑权重排序
```

**demo 页容器类型的适配（现有 11 种 A-K 不变）：**

| 容器 | 适合 Project | 适合 Post |
|------|-------------|-----------|
| A 大图 | 编辑精选产品 | 精选 build log、重磅复盘 |
| B 标准卡 | 产品展示 | 带图的产品发布帖 |
| C 紧凑行 | 产品列表 | 工具推荐、资源合集 |
| D 文字块 | — | 策略洞察、方法论摘要、想法 |
| G 排行榜 | 热门产品 | 热门经验帖 |
| H 轮播 | 最新产品 | 最新 Post |
| I 引述 | — | Post 中的金句 |
| K 通栏 | 平台统计 | 周报/里程碑 |

## 三、信息密度评分

### 3.1 定位

评分的作用是**把候选池从几千条缩小到几百条**，让编辑的时间花在刀刃上。不是替代编辑判断。

实际审核证明：一些算法低分（10-11 分）的内容被编辑通过了（小而美的创意产品），高分的被跳过了（无差异化的跟风产品）。编辑判断 ≠ 算法打分，品味是核心壁垒。

### 3.2 评分不是单一总分

避免把信息密度、热度、时效混成一个数字。分轴独立展示，让编辑带着上下文判断：

| 维度 | 衡量什么 | 信号 |
|------|----------|------|
| **密度** | 内容本身的信息含量 | 具体数字、步骤描述、具名工具/产品、外部链接、图片、内容长度 |
| **热度** | 社区验证程度 | 点赞、评论数、评论质量、是否 featured |
| **时效** | 新鲜程度 | 发布时间距今 |
| **关联** | 实体提取后的关联丰富度 | 关联了多少个已知 project/maker |

展示时可以算加权总分用于排序，但编辑应能看到每个维度的独立值。这样"密度高但热度低"的冷门好内容不会被系统性错杀。

### 3.3 高密度信号

- 包含具体数字（收入、用户量、转化率、天数、成本）
- 包含具体步骤/流程（>100 字的结构化描述）
- 包含多个具名工具/产品/服务
- 包含外部链接（产品链接、代码仓库、教程地址）
- 包含图片/截图
- 有高质量评论（评论中有补充信息、使用体验）
- 作者有明确的 maker 身份

### 3.4 直接丢弃（硬过滤，不进评分）

- 极短内容（<50 字 + 无链接 + 无图片）
- 招聘/求职/内推
- 转发抽奖/营销水帖
- 纯情绪发泄无具体信息

### 3.5 编辑品味补充维度（算法难以量化）

- 产品有审美/创意（小而美，哪怕数据不高）
- 创始人故事有独特性
- 切入点冷门但有价值（"外卖比价"、"文学时钟"）
- 失败案例但有诚意的反思

## 四、数据处理管道

### 4.1 管道顺序

```
原始数据 → 标准化 → 实体提取 → 密度评分 → 过滤 → 审核队列
```

**关键：先提取再过滤，不是先过滤再提取。** 有些帖子单看内容像闲聊，但提取实体后发现提到了 3 个产品——这种不应被提前错杀。

### 4.2 各环节职责

| 环节 | 输入 | 输出 | 说明 |
|------|------|------|------|
| 原始数据 | 各源 adapter 输出 | RawItem | 落盘到 `data/raw/{source}/`，不可变 |
| 标准化 | RawItem | StandardItem | 提取公共字段 + 保留源特有字段到 source_extra |
| 实体提取 | StandardItem | StandardItem + 实体引用 | 从内容中识别 project/maker 引用（链接匹配 + 名称匹配） |
| 密度评分 | StandardItem + 实体引用 | 带分数的 Item | 多维评分：密度、热度、时效、关联 |
| 硬过滤 | 带分数的 Item | 候选池 | 只丢弃明确的垃圾（<50字水帖、招聘、抽奖） |
| 审核队列 | 候选池 | 飞书/平台审核表 | 按总分排序，展示各维度分数，供编辑判断 |

### 4.3 Adapter 模式

每个数据源是独立 adapter：

```
scripts/crawl/
  jike.ts           # 即刻 adapter
  producthunt.ts    # PH adapter
  {new_source}.ts   # 未来新渠道
  config.json       # 统一配置
```

Adapter 职责：连接源 → 拉取 → 转为 RawItem → 存储。不做过滤、不做评分。

### 4.4 当前实现与目标的差距

| 目标 | 当前状态 | 差距 |
|------|----------|------|
| 先提取再过滤 | 即刻脚本先过滤再提取 | 需要调整顺序 |
| 原始不可变 | PH 脚本抓取时按 minVotes 丢弃 | 应存全量，评分时再过滤 |
| 统一 RawItem | 每个源各自落盘格式不同 | 需要定义标准层 |
| 多维评分 | 单一总分 | 需要拆分维度 |

这些差距是冷启动阶段的务实捷径，后续逐步对齐。

## 五、编辑审核工作流

### 5.1 当前方案：飞书多维表格

- 飞书 Base: `KXYpb5pTUa5gnPsFe18cNaoVnzh`
- 按来源/批次建表，推送待审数据
- 审核字段：通过 / 跳过 / 待定
- 备注字段：类型标签、关注点、疑虑
- 两人协作：万逸轩 + 万宇轩，从两端向中间审核

### 5.2 审核判断标准（来自 68 条实际审核记录）

**通过倾向：**
- 有明确可用产品 + 创作者叙事（TypeNo、FateTell、拾刻文学时钟）
- 高信息密度经验复盘（独立开发 2 年总结、Claude Code 最佳实践）
- 小而美 + 有创意/审美的产品（中国色测试、人生节气、比比怪）
- 实用开源工具（ai-daily-digest、nuwa-skill）
- 出海实战经验、MRR 里程碑分享

**待定倾向：**
- 需要下载体验才能判断的 App
- 有风险的灰色地带产品
- 已经很知名，不确定收录价值的

**跳过倾向：**
- 无差异化的跟风产品（"一般，很多人做了"）
- 知名但不符合平台审美（"理念一般"）

### 5.3 已知不足（后续迭代）

- 缺少跳过原因枚举（目前只靠备注文字，不易统计）
- 缺少跨编辑一致性校准（两人标准可能漂移）
- 缺少抽样重审机制

## 六、冷启动 → 原生过渡

### 6.1 阶段定义

| 阶段 | 数据来源 | 重点 |
|------|----------|------|
| 冷启动（当前） | 爬取外部平台 | 积累高质量内容池，建立初始品牌感知 |
| 吸引期 | 爬取 + maker 发现自己被收录 | maker 来到平台查看 |
| 过渡期 | 爬取 + 原生投稿 | maker 认领 profile + 直接发布 |
| 原生期 | 以原生为主，爬取为辅 | 社区自运转 |

### 6.2 Maker 认领机制

冷启动阶段自动创建的 Maker profile，当本人来到平台时可认领。

**认领流程：**
1. 用户声明"这是我" → 选择一个已有的 source_ref（如即刻账号）
2. 验证：在原平台发一条包含特定验证码的内容（或其他可行验证方式）
3. 认领成功前，先展示即将合并的内容，让用户确认
4. 认领后可修正/补充信息

**风险控制：**
- 合并前展示预览，让用户确认"这些确实是我的"
- 认领后发现错误可以拆分/退出
- 提供"不想被收录"的退出机制

### 6.3 不要假设过渡是自然发生的

被收录不一定带来认领，也可能带来反感、纠错请求、或沉默。需要关注：
- 有多少 maker 实际来看了自己的 profile
- 有多少做了认领 vs 要求删除
- 认领后有多少人继续贡献原生内容

没有这些信号，就无法判断冷启动数据是否真的在转化为社区。

## 七、远期方向（不急于现在实现）

以下方向在理论上有价值，但在当前阶段（数据量 <1 万条，1+1 人团队，产品未上线）实现会过度工程化。记录在此，待规模增长后启动。

1. **知识原子层** — 从 Content 中提取可复用的结构化洞察（MRR 数字、获客方法、定价策略）作为独立实体。等内容积累到一定量后用 AI 做二次提取。

2. **置信度模型** — 实体合并时的自动化匹配 + 置信度评分 + 人工确认。等数据量到 10 万+ 或开放用户认领时再需要。

3. **衡量体系** — review precision@k、编辑通过率、实体合并误伤率、认领转化率。需要数据流过系统后才能测量。

4. **完整的 Bronze → Silver → Gold 数据管道** — 生产级的不可变存储 + 增量更新 + 版本快照。等数据量和团队规模支撑时再建。
